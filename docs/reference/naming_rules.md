# 命名ルール

## 1. 目的

命名ルールは、コードの読みやすさ、責務の明確化、保守性の向上を目的とします。

## 2. 基本方針

### 2.1 クラス名

- クラス名は名詞または責務を表す名詞句にする
- 役割が明確にわかる名前を用いる
- 例: `GeminiClient`, `PromptContextModel`, `WorkflowEditor`

### 2.2 メソッド名

- 動詞から始める
- 生成・編集・設定・取得などの意図が明確であることを優先する
- 例: `generate_text()`, `set_authentication()`, `apply_modifications()`

### 2.3 定数と Enum

- Enum のメンバーは上位概念を表す大文字スネークケースを採用する
- 例: `GEMINI_2_5_PRO`, `BLOCK_ONLY_HIGH`, `SAFE`
- 文字列値には実際の API パラメータの値を持たせる

### 2.4 属性名

- オブジェクトの状態や設定を表す名詞を用いる
- 例: `project_id`, `api_key`, `base_url`, `polling_interval`
- private 属性には `_` を付けて内部状態であることを明示する

## 3. ルールの観点

### 3.1 役割と名前の整合

名前が役割と一致していることを重視します。たとえば、`WorkflowEditor` は編集処理そのものを担うための名前であり、単なるデータ容器ではありません。

### 3.2 API 名とドメイン名の混在を避ける

プロバイダー固有の名称をそのままクラス名に詰め込みすぎると、責務が曖昧になります。`BaseAIClient` などの抽象名を使い、実装との差異を吸収する設計を推奨します。

### 3.3 省略形の使用は最小限にする

`uwgen`、`gemini`、`ai` のような略語は便利ですが、文脈によっては意味が曖昧になります。長くても明確な名前を選ぶことを優先します。

## 4. 現行実装の整理

現状の実装では、命名はおおむね一貫しています。

- `GeminiClient` / `ImagenClient` / `UwgenClient` : 実サービス別クライアント
- `BaseAIClient` / `BaseGeminiClient` : 抽象的な共通基盤
- `PromptContextModel` : 生成時の入力状態を表すモデル
- `WorkflowEditor` : 操作対象としての編集責務

一方で、`initialize_app.py` や `app_init.py` のような初期化 API の表現がやや混在しているため、正式な入口名と非推奨名を明確にして命名の意図を統一するとよいです。

## 5. 推奨実装ルール

- 役割が実装と一致する名前にする
- 既存の命名規則を壊さず、意味を補完する
- 一貫性が失われる場合は、API や設定のラッパー関数に一段の名前を追加する
- 例外名や設定名は、起こりうる失敗や状態をそのまま表す形にする

命名ルールは、コードレビューの見落としを減らし、将来の機能追加時に受け入れやすい基準として役立ちます。
