# コーディングルール

## 1. 目的

本ドキュメントは、AI 連携と生成系ロジックを持つ Python コードを、読みやすく、拡張しやすく、障害時に診断しやすい形で維持するための指針を定義します。

## 2. 基本原則

### 2.1 役割の明確化

各クラスは 1 つの責務に集中し、以下のような分離を維持します。

- 設定管理
- API 通信
- 例外表現
- ドメインモデル
- 生成ワークフロー補助

### 2.2 抽象化の優先

具体的な API 実装を利用側に直接持たせるよりも、抽象基底クラスや共通基盤を経由して利用する設計を優先します。これにより、プロバイダー差異を吸収しやすくなります。

### 2.3 設定値の型化

設定は `Enum` や設定モデルとして定義し、文字列の散在を避けます。`GeminiModel`、`AspectRatio`、`SafetyFilterLevel` などのような定数群は、実装の整合性を保つ上で重要です。

### 2.4 例外を明示的に扱う

API レベルの失敗とアプリケーションレベルの失敗は、区別して扱います。呼び出し側が `NoCandidatesError` や `APIError` を区別できる設計にします。

## 3. 実装指針

### 3.1 クラス設計

- 共通機能は基底クラスへ寄せる
- クライアントは API の差異を吸収する薄いラッパーとして実装する
- 設定やドメインモデルは構造データとして扱う
- 補助ロジックは再利用可能な関数やユーティリティに分離する

### 3.2 関数設計

- 引数の意味を明確にする
- 戻り値は構造化データとして返す
- 失敗時は例外で明示し、`None` に頼りすぎない
- 非同期処理であれば、再試行とタイムアウトが明示的であることを優先する

### 3.3 依存管理

- 外部依存は URL、キー、環境設定、認証情報として外部化する
- SDK 의細部に直接依存しすぎないようにする
- 実装に入る前に、依存先がどこで初期化されるかを把握する

## 4. 既存実装に見られる良い点

現状のコードでは、以下の実装スタイルが本ルールと整合しています。

- `BaseAIClient` に共通処理を集約している
- `BaseGeminiClient` に Enum ベースの設定を持たせている
- `PromptContextModel` に生成プロンプトの構造を保持している
- `WorkflowEditor` にワークフロー差分適用の責務を切り出している

## 5. 注意点と改善候補

下記は、将来の整理で注意すべき事項です。

- `app_init.py` での非推奨警告は、API と利用側の契約を曖昧にする
- 重複した初期化ロジックや外部依存の強さを、少しずつ整理する必要がある
- 後続の開発者が理解しやすいように、例外と設定のコメントを維持する
- 将来の拡張時は、共通インターフェースに対する破壊的変更を避ける

## 6. 推奨ルール

- すべての設定値は Enum または設定モデルに置く
- 例外は種類ごとに分類し、メッセージを具体化する
- 再試行はタイムアウトや制約とセットで設計する
- 生成ロジックは API の詳細を吸収したラッパー内に閉じ込める
- ドキュメントと実装がズレていないかを定期的に確認する

本ルールは、柔軟な生成系アプリケーションを保守し続けるための実装ガイドとして機能します。
