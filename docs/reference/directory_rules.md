# ディレクトリルール

## 1. 目的

本プロジェクトのディレクトリ構造は、設定、抽象基盤、API クライアント、ドメインモデル、および補助機能を分離して管理するために設計されています。

## 2. 主要ディレクトリの責務

### 2.1 `configs/`

設定とアプリケーション初期化の責務を持ちます。

- `PyCorexConfig` による設定集約
- `init_app()` による初期化の入口
- 環境依存の設定管理

### 2.2 `core/`

共通の抽象基盤と固有 API のベースインターフェースを管理します。

- `BaseAIClient`
- `BaseGeminiClient`
- `BasePromptGenerator`

この層は、実装の共通口を提供する役割を持ちます。

### 2.3 `models/`

設定モデルやプロンプト関連データ構造を保持します。

- `GeminiModel`, `VertexaiModel` などのモデル定義
- `PromptContextModel` などの構造化データ

### 2.4 `utils/`

再利用可能な補助機能を格納します。

- プロンプト生成のファクトリと実装
- ワークフロー編集支援
- 生成パラメータの加工

### 2.5 `exceptions/`

実行時に発生する失敗と制約違反を表現する例外を管理します。

- `APIError`
- `ComfyUIAPIError`
- `NoCandidatesError`

### 2.6 `enums/`

列挙型を配置し、構造化された定数として扱います。

- `RatingLevel`
- 生成時に必要な安全性・評価レベルの定義

## 3. 配置原則

- 実装詳細は最小単位に分離する
- API 依存はクライアントに閉じ込める
- 設定は `configs/` と `models/` で明確に分ける
- 共通処理は `core/` に置く
- 再利用ユーティリティは `utils/` に置く

## 4. ルールと監査観点

### 4.1 役割を超えた責務を持たせない

たとえば、クライアントが設定読み込みまで担うような設計は避けるべきです。設定責務と実行責務は分離します。

### 4.2 レイヤー間の依存方向を維持する

上位レイヤーが下位レイヤーに依存する方向を維持し、逆方向の依存を押し込まないようにします。

### 4.3 新規追加時の配置方針

新しいサービスや機能を追加するときは、次の優先順位で配置します。

1. 共通基盤に適合するか確認する
2. `models/` に設定モデルが必要か確認する
3. `exceptions/` で失敗条件を定義する
4. 実際の API 実装を `comfyui_client.py` などのプロバイダー層へ置く
5. 必要に応じて `utils/` に補助機能を置く

## 5. 現行実装との整合性

現状の実装では、上記の分離がほぼ満たされています。

- `core/` に共通抽象が置かれている
- `configs/` と `models/` が役割分担されている
- `exceptions/` が例外定義を保持している
- `utils/` が生成補助とワークフロー支援をまとめている

ただし、初期化系のパスが複数存在することや、`libcore_hng` 依存の範囲が大きいことは、今後の整理対象です。

## 6. 今後の改善方針

- 初期化ロジックを 1 つの正式な入口へ集約する
- 外部依存の境界と内部責務の境界を明確にする
- 追加モジュールを新しいディレクトリに勝手に作らず、責務に応じて配置する

本ルールは、拡張性と保守性を両立させるための配置戦略として機能します。
