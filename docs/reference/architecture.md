# アーキテクチャ

## 1. 基本方針

本プロジェクトのアーキテクチャは、AI 提供元の違いを吸収しつつ、アプリケーションコードから共通インターフェースを扱えるようにすることを目的としています。実装上は、以下のレイヤーに分かれています。

1. アプリ初期化と設定レイヤー
2. 共通基盤レイヤー
3. プロバイダー別クライアントレイヤー
4. ドメインモデルと Enum レイヤー
5. 補助機能レイヤー

## 2. レイヤー構成

### 2.1 アプリ初期化と設定レイヤー

`configs/` 配下では、`PyCorexConfig` と初期化補助が管理されています。これはアプリケーションの起動時に環境依存の設定を収集し、各クライアントや機能が参照できるようにする役割を担います。

- `configs/pycorex.py` : 複数の設定モデルを集約
- `configs/app_init.py` : 初期化ラッパー関数と AppInitializer の呼び出し
- `configs/initialize_app.py` : 代替初期化パスとしての設計想定

> 現実装では `app_init.py` に非推奨の警告が存在するため、将来の設計では初期化 API を 1 つに統一することが望まれます。

### 2.2 共通基盤レイヤー

`core/` 配下には、AI クライアントやプロンプト生成の抽象基底が配置されています。

- `BaseAIClient` : 再試行、ファイル名生成、MIME 判定などの共通処理
- `BaseGeminiClient` : Gemini 系機能に共通する Enum と基礎定義
- `BasePromptGenerator` : 生成責務の抽象インターフェース

この層は、サービス実装ごとの差異を吸収するための契約を定義する役割を持ちます。

### 2.3 プロバイダー別クライアントレイヤー

実際の API 連携は、以下のクライアントが担当します。

- `gemini_client.py` : Gemini 用テキスト生成クライアント
- `imagen_client.py` : Imagen 用画像生成・編集クライアント
- `uwgen_client.py` : Uwgen 用統合クライアント
- `comfyui_client.py` : ComfyUI 用ワークフロー実行クライアント

これらは `BaseAIClient` を継承し、プロバイダー固有の `generate_*` / `edit_*` / `analyze_*` などを実装します。

### 2.4 ドメインモデルと Enum レイヤー

`models/` と `enums/` は、設定情報や業務上の状態を表現するオブジェクトを保持します。

- `PromptContextModel` : 生成対象に必要な入力値と出力条件の構造化
- `PromptModel` : プロンプト関連設定
- `GeminiModel` / `VertexaiModel` / `UwgenModel` / `ComfyUIModel` : API 利用設定モデル
- `RatingLevel` : コンテンツレベルの評価ルール

### 2.5 補助機能レイヤー

`utils/` には、生成ロジックやワークフロー制御に関する補助が置かれています。

- `PromptGenerator` : ジェネレーターを登録・取得するファクトリ
- `PonyPromptGenerator` : 具体的な生成ロジック
- `WorkflowEditor` : ComfyUI ノード修正の適用
- `WorkflowMod` : ワークフロー修正の補助意図を持つユーティリティ

## 3. 依存方向

設計上の依存方向は、概ね次の通りです。

- `configs` は `models` と外部設定基盤を参照する
- `core` は `models` と `exceptions` に依存しうる
- 各 client は `core` と `exceptions` を継承・利用する
- `utils` は `core` と `models` を利用し、必要に応じて client を呼び出す

## 4. 設計上の特徴

### 4.1 抽象化された拡張性

新しい AI プロバイダーを追加する場合でも、以下の順で対応できます。

- 共通基底クラスの契約を確認する
- 対応する設定モデルと Enum を定義する
- プロバイダー用クライアントを実装する
- 必要に応じて `PromptGenerator` などの利用の入口を追加する

### 4.2 例外ベースの分離

API 起因の失敗とアプリケーションの制約違反は `exceptions/` に分離されているため、実行時例外を利用側が判別しやすい構造です。

### 4.3 アプリケーション初期化の外部化

実際には `libcore_hng` に依存して初期化されているため、責務の中心はパッケージ内実装ではなく、外部の設定基盤との接続に置かれています。これは、再利用性を高める一方で、設計の境界を明確にする必要があります。

## 5. 不整合と検討事項

以下は現状の実装と設計のズレとして認識すべき点です。

- `app_init.py` と `initialize_app.py` の役割が競合している
- 外部ライブラリ `libcore_hng` に対する依存が強い
- 例外定義と利用側の責務が十分に明文化されていない
- 生成ロジックと設定ドメインが一部で混在している

これらは設計変更の対象として扱うべきです。特に初期化 API の整理は、今後の拡張性に大きく影響します。

## 6. 設計指針

今後の設計では、次の原則を優先することが適切です。

- 外部環境依存の初期化ロジックをパッケージ境界で明確化する
- AI サービス固有の実装を共通抽象から分離する
- 設定と実行ロジックの分離を維持する
- 例外のレベルと契約を設計文書に明文化する
- ワークフロー編集や生成ロジックの再利用性を維持する

本リポジトリのアーキテクチャは、生成系アプリケーションの中核として十分に整理されていますが、外部依存の明示と初期化統一を行うことで、より堅牢な構造になります。
