# ビジネスルール

## 1. 目的

本ドキュメントは、AI 連携を行うアプリケーションとしての利用方針と、生成系 API を安全かつ再利用しやすく扱うための制約を整理します。

## 2. 主な利用目的

このリポジトリで扱う主要なユースケースは、次のとおりです。

- テキスト生成
- 画像生成
- 画像編集
- 画像解析
- 生成ワークフローの自動化
- プロンプト生成の構造化

## 3. 主要ルール

### 3.1 生成系 API の責務分離

テキスト生成、画像生成、画像編集は、同一の UI ロジックに結びつけず、それぞれのクライアントやメソッドで分離して扱います。これは、利用目的や API 制約が異なるためです。

### 3.2 安全性とフィルタリング

Gemini や Imagen の実装では、危険カテゴリや人物生成の許可範囲、出力サイズ、アスペクト比などを列挙型で表現しています。これにより、生成時の安全設定を合意可能な粒度で制御します。

### 3.3 コンテンツ評価レベルの定義

`RatingLevel` は、生成するプロンプトや出力内容のリスク水準を段階的に管理するための基盤です。これは、コンテンツの安全性を明示的に扱うための設計です。

### 3.4 失敗時の継続性

生成 API は一時的なエラーや候補不足に直面する場合があります。`execute_with_retry()` のような再試行処理と、`NoCandidatesError` のような例外クラスにより、利用側で失敗時の制御を可能にしています。

## 4. 生成ワークフローに関する要件

- 生成対象のモデルや設定値は構造化されて管理する
- 画像生成の前後で、プロンプト条件や設定を変換可能にする
- ComfyUI のノード修正は、ワークフローの更新を一時的な差分として扱う
- 生成時のログは、再現性とデバッグ性を確保するための情報を持つ

## 5. 事業上の設計原則

- API 依存は抽象化して管理し、外部仕様変更の影響範囲を最小化する
- 生成モデルの違いを実装側で埋め込まず、利用側から統一的に扱えるようにする
- 画像やプロンプトの出力は、型や構造化データとして扱う
- 生成前後の制約と安全ガードを設定レベルで管理する

## 6. 既存実装との整合性

現在のコードでは、以下のルールが実装に反映されています。

- Gemini / Imagen / Uwgen などサービス別の責務分離
- RatingLevel によるリスク階層の表現
- ComfyUI ワークフロー編集の差分適用
- 例外的な候補不足とAPI失敗の分離

一方で、以下は事業ルールとして明文化すべきです。

- 初期化 API の旧新混在は運用上の非統一である
- 外部設定基盤への依存度を明示し、プロダクト単位の責務境界を整理する必要がある
- 生成サービスごとの利用条件の維持とドキュメント更新を継続的に行う必要がある

## 7. 実務上の推奨事項

- 新しいモデルやサービスを追加する際は、必ず安全設定と失敗条件を併せて定義する
- 生成の設定値は Enum で管理し、文字列散在を避ける
- 利用者が無視できない制約は、例外で明示する
- API 仕様更新時は、モデル定義と設定構造の両方を更新対象に含める

本ルール群は、AI 生成系アプリケーションとしての利用目的と、実装の保守可能性の両方を保持するための設計基準として位置づけられます。
