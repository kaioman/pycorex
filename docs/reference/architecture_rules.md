# アーキテクチャルール

## 1. 目的

アーキテクチャルールは、AI 連携と生成系ワークフローを拡張しやすい状態で維持するための境界と原則を定義します。

## 2. 基本原則

### 2.1 責務の分離

各モジュールは、次のいずれかの責務に収まるように設計します。

- 設定定義
- 共通基盤
- API 接続
- 例外処理
- ドメインモデル
- 補助ロジック

責務が重なる場合は、レイヤーの再分割を検討します。

### 2.2 共通抽象の活用

AI プロバイダー固有の実装は `BaseAIClient` や `BaseGeminiClient` などの抽象基盤に依存する形にし、実装側では共通メソッドを再利用します。

### 2.3 設定の外部化

設定値はモジュール内部に埋め込まず、設定モデルとアプリ初期化経路を介して供給することを原則とします。これにより、動作環境や API キー管理の影響範囲を限定できます。

### 2.4 例外の種類を明確化する

API 呼び出しの失敗、候補取得の失敗、プロンプト生成の失敗は、単一例外に統合せず、責務に応じた例外クラスを使用します。

## 3. 境界条件

### 3.1 プロバイダー層

プロバイダー層では、API の詳細仕様に依存する実装を記述します。ただし、API 呼び出しの具体的な実装詳細は、利用側に露出させず、共通結果形式へ変換する設計を推奨します。

### 3.2 モデル層

モデル層では、設定値やドメインデータの構造を定義し、ビジネスロジックそのものを含めないようにします。

### 3.3 補助機能層

ワークフロー編集やプロンプト生成などの補助機能は、共有された処理を提供する役割に留め、外部依存の実体を直接実装しないようにします。

## 4. 拡張性ルール

- 新しい AI サービスを追加する場合は、既存の共通抽象を最優先で再利用する
- 生成ロジックはプロバイダー固有の実装と分離する
- 設定変更は設定レイヤーに閉じ込め、呼び出し側のシグネチャを過度に変えない
- 依存関係は上位レイヤーから下位レイヤーへの一方向に保つ

## 5. 運用上の指針

### 5.1 非推奨 API の管理

`init_app()` のような旧来の初期化 API は、設計上の移行期間として扱い、将来的に一本化する方針を明示します。

### 5.2 ログと監視

AI API 呼び出し時のリトライや失敗は、ログに残しやすい設計にすることが望まれます。特に生成指示、対象モデル、失敗タイミングを記録できるようにするのが望ましいです。

### 5.3 互換性確認

追加機能や設定項目を導入する際は、既存の API 呼び出しやワークフロー設定との互換性を評価します。

## 6. 現行実装との整合性

現在の実装では、以下の方針が実際に観測されます。

- 共通基底と各サービスクライアントの分離が明確
- `models` と `configs` の責務が概ね分離されている
- `exceptions` の設計が失敗条件の識別に有効

一方で、以下は設計整理の対象です。

- 初期化 API の二重化
- 外部依存の境界がやや曖昧
- 設定と実行ロジックの統合度が環境依存の影響を受けやすい

これらの整理が進むことで、拡張性と保守性が高まります。
