# テストルール

## 1. 目的

本ドキュメントは、生成系 AI アプリケーションにおける品質保証の基本方針を整理します。特に、外部 API 依存の強いコンポーネントでは、安定した回帰防止と再現性が重要です。

## 2. 基本方針

### 2.1 外部依存の分離

Gemini、Imagen、Uwgen、ComfyUI の各 API は外部サービスに依存しているため、テストでは API 呼び出しそのものを直接実行しない設計を優先するのが望ましいです。

- 通信層のモック化を最低限に留める
- 実装の末端に近い振る舞いを検証する
- API 失敗時の例外分岐を確認する

### 2.2 例外系の検証

`NoCandidatesError`、`APIError`、`ComfyUIAPIError` のような例外は、発生条件とメッセージの意図がテストで確認されるべきです。

### 2.3 リトライロジックの検証

`BaseAIClient.execute_with_retry()` のような再試行処理は、成功時と失敗時の両方をテスト対象とします。特に、失敗回数と待機間隔の期待値が正しく保たれているかを確認します。

## 3. テスト観点

### 3.1 API 連携テスト

- 接続失敗時に適切な例外が送出されるか
- `HTTPStatus` やレスポンス内容に応じて例外が正しく分岐するか
- 空の結果や null 値が返ったときに `NoCandidatesError` などに変換されるか

### 3.2 生成ロジックテスト

- `PromptContextModel` が期待した値を保持するか
- `PromptGenerator` が登録されたジェネレーターを正しく返すか
- ワークフロー編集時に対象ノードが正しく更新されるか

### 3.3 設定テスト

- `PyCorexConfig` が想定した設定モデル群を保持するか
- 初期化時に設定ファイルや構成が正しく反映されるか

## 4. 回帰防止の観点

- 新しい API モデル追加時に `Enum` の値と API パラメータが同期しているか確認する
- 既存のプロンプト生成ロジックを壊さないように、生成結果の形式をテストする
- `WorkflowEditor` のノード更新が、既存ワークフローと衝突しないことを確認する

## 5. 現行実装との整合性

現状の構成では、以下のテスト観点が有効です。

- 共通基盤の挙動
- 例外の分岐
- ComfyUI ワークフロー編集
- プロンプト生成の契約

一方で、初期化 API の旧新混在や外部設定依存の強さは、テスト戦略上の影響も考慮する必要があります。

## 6. 推奨ルール

- API 呼び出しの検証では、実ネットワーク依存を最小化する
- 生成ロジックのテストでは、入力と出力の構造を固定する
- 例外の分岐は、実際の失敗条件に合わせて検証する
- リトライやタイムアウトの仕様変更時は、テストを更新する
- 「動作確認できる最小の再現ケース」を優先する

本ルール群は、生成系 AI ソフトウェアにおいて重要な安全性と再現性を確保するための基準です。
